# TusLibros.com - Iteration 4: System Facade, Sessions and Time

## Starting code

`starting/TusLibros-33.st`: iterations 1 to 3 (`Cart` over a price list, `Cashier` debiting through a simulated Merchant Processor and registering `Sale`s, `CreditCard`, `StoreTestObjectsFactory`, `CartTest` 8 tests and `CashierTest` 6 tests). This iteration adds behaviour to it and reshapes the cashier's output.

## Scope of this iteration

Model the object the REST layer will talk to. It offers the five operations of the statement as messages (not yet as HTTP nor as `0|...` strings) and enforces the client authentication and the 30-minute validity of the carts:

1. **Create cart** (`/createCart`): given a client id and a password, validate that the client may operate with TusLibros.com ("Invalid user and/or password" otherwise) and answer the id of a new, empty cart. The facade generates the id (not the cart), for security and to avoid exposing an internal id; the example uses consecutive numbers and says a real system must not.
2. **Add to cart** (`/addToCart`): given a cart id, a book and a quantity, add the book to that cart. The cart id must be one the facade created ("Invalid cart id"); the book must be in the catalog and the quantity positive, with the cart's own messages.
3. **List cart** (`/listCart`): given a cart id, answer the cart's content (books with their quantities, i.e. something that answers `occurrencesOf:` and `isEmpty`).
4. **Check out cart** (`/checkOutCart`): given a cart id, a credit card number, its owner's name and its expiration month, check the cart out through the cashier with the facade's Merchant Processor and sales book; the empty-cart and expired-card errors of the cashier are propagated; the sale is registered for the client who owns the cart. (The card number and owner name are received but not validated nor stored: the `CreditCard` only knows its expiration.)
5. **List purchases** (`/listPurchases`): given a client id and password (authenticated as in 1), answer, per book bought by that client, the total amount spent on it.
6. **Validity of a cart** (statement: "valid for 30 minutes after the last operation performed with it"): every operation on a cart id checks that the cart's session has not expired ("Can not use the cart after 30 minutes of inactivity") and, when it has not, records the time of the operation. The test must be in control of time, so the facade takes the current time from a clock it receives and the tests use a manual clock they can advance (`advanceTime:`) and revert (`revertTime:`).

## What the solution (`TusLibros-78.st`) contains

- Categories `TusLibros-Model` and `TusLibros-Tests` (the starting code uses `TusLibros`).
- `TusLibrosSystemFacade authenticatingWith: aValidUsersAndPasswords acceptingItemsOf: aCatalog registeringOn: aSalesBook debitingThrought: aMerchantProcessor measuringTimeWith: aClock`. Protocol: `createCartFor:authenticatedWith:` -> cart id; `add:of:toCartIdentifiedAs:`; `listCartIdentifiedAs:` -> the cart's content (a copy of its `Bag`); `checkOutCartIdentifiedAs:withCreditCardNumbered:ownedBy:expiringOn:` -> the ticket; `listPurchasesOf:authenticatingWith:` -> `Dictionary` book -> amount; `sessionDuration` (`30 minutes`); `now`, `today`; error descriptions `invalidUserAndOrPasswordErrorDescription`, `invalidCartIdErrorDescription`, `sessionHasExpiredErrorDescription`, plus the cart's and cashier's messages re-exposed. Authentication: `does:authenticatesWith:` against a `Dictionary` user -> password (a real system would store hashes). Cart ids: `generateCartId`, consecutive integers.
- `CartSession ownedBy: aCustomer with: aCart on: aSystemFacade`: `lastUsedTime`; `do: aBlock` asserts `isExpiredAt: now` (`lastUsedTime + sessionDuration < now`) and, in an `ensure:`, updates `lastUsedTime`; `addToCart:of:`, `cartContent`, `checkOutCartWithCreditCardNumbered:ownedBy:expiringOn:` (creates the `Cashier` with the facade's Merchant Processor and sales book, `on: self today`).
- `Clock` (`now`, `today` from `DateAndTime now`) and, in the tests, `ManualClock now: aTime` with `advanceTime:` / `revertTime:`.
- `Cashier toCheckout:ownedBy:charging:throught:on:registeringOn:`: `checkOut` creates a `Ticket of:` `LineItem`s (`of:quantity:total:`, computed from `cart itemsAndQuantitiesDo:` and the catalog), debits `ticket total` through the Merchant Processor, registers `Sale doneBy: owner certifiedWith: ticket` and answers the ticket. `Sale>>wasDoneBy:`, `total`, `lineItemsDo:`. `Cart` keeps its items in a `Bag` and adds `content` and `itemsAndQuantitiesDo:`; errors are signalled through `signalInvalidItem` / `signalInvalidQuantity`.
- `MerchantProcessor`: an abstract class with `debit:from:` as subclass responsibility and a `README` method explaining it exists only to document the protocol every Merchant Processor must answer (no class subclasses it; the tests keep playing the role).
- `TusLibrosSystemFacadeTest`, 19 tests: create cart `test01CanCreateCartWithValidUserAndPassword`, `test02CanNotCreateCartWithInvalidUser`, `test03CanNotCreateCartWithInvalidPassword`; add to cart `test04CanAddItemsToACreatedCart`, `test05CanNotAddItemToNotCreatedCart`, `test06CanNotAddItemNotSellByTheStore`, `test17CanNotAddToCartWhenSessionIsExpired`; list cart `test07ListCartOfAnEmptyCartReturnsAnEmptyBag`, `test08CanNotListCartOfInvalidCartId`, `test09ListCartReturnsTheRightNumberOfItems`, `test18CanNotListCartWhenSessionIsExpired`; checkout `test10CanCheckoutACart`, `test11CanNotCheckoutANotCreatedCart`, `test12CanNotCheckoutAnEmptyCart`, `test13CanNotCheckoutWithAnExpiredCreditCard`, `test19CanNotCheckOutCartWhenSessionIsExpired`; list purchases `test14ListPurchasesIncludesBoughtItems`, `test15CanNotListPurchasesOfInvalidCustomer`, `test16CanNotListPurchasesOfValidCustomerWithInvalidPassword`. The test case is the Merchant Processor (`merchantProcessor ^self`, `debit:from:` doing nothing). 33 tests in total.
- Steps: the facade is called `RestInterface` from snapshot 35 to 75 (its test `RestInterfaceTest` appears in 34); `CartSession` appears in 57, `LineItem` and `Ticket` in 61, `ClockForTesting` in 69 and `Clock` in 73, `MerchantProcessor` and the category split in 74; 76 and 77 are alternative endings (`TusLibrosSystemFacade` in category `TusLibros`; `InterfaceRest`) and 78 is the final one.

## Not part of this iteration

The `0|...` / `1|ERROR_DESCRIPTION` encoding of the answers, HTTP 200/400 and the outer (string) side of the interface; the batch files of V3 (or, in V2, saving the transaction to a file when the Merchant Processor is down); the validation of the credit card number and owner name (maximum 30 characters); the real Merchant Processor's HTTP protocol. The reference notes list "test that the create-cart answer is the expected string" and "test that more than 30 minutes pass", of which only the second is in the code.
